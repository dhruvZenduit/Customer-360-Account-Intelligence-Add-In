# CUSTOMER 360 → PORTFOLIO COMMAND CENTER

## Phased Build Plan — Customer Portfolio Health & Action Scorecard

You are working inside an EXISTING **Customer 360 / Account Intelligence Add-In**.

Do NOT create a separate application.

Do NOT replace the existing Customer 360 functionality.

The task is to add a new **Customer Portfolio Health & Action Scorecard / Command Center**
layer on top of the existing Customer 360 system, transforming it from a passive
account-information dashboard into an actionable portfolio command center.

# 1. PRODUCT GOAL

The system continuously reviews customer signals and answers four questions:

> **1. How healthy is this customer?**

> **2. How urgently should we act?**

> **3. Why is this customer receiving this priority?**

> **4. What specifically should we do next?**

It must produce THREE separate primary outputs:

```text
HEALTH SCORE
How healthy is the account?

PRIORITY SCORE
How urgently should someone act?

RECOMMENDED ACTION
What specifically should happen next?
```

Do NOT collapse these into one score.

A customer can have:

```text
Health: 75
Priority: P1 / 91
```

because the account is generally healthy but has a critical unresolved camera issue.

Another customer could have:

```text
Health: 42
Priority: P3 / 48
```

because the account is unhealthy but there is no immediate action required.

If the implementation cannot produce both of those, health and priority are still
coupled somewhere. That is the single most important thing this plan protects.

# 2. THE PIPELINE

```text
Existing Customer 360 data
        ↓
Device/Product Health
Support Health
Relationship Health
Commercial/Retention Health
Outcome/Value Health
        ↓
HEALTH SCORE
        +
Critical Overrides
        ↓
PRIORITY SCORE
        ↓
SAVE / FIX / GROW / ENGAGE
        ↓
RECOMMENDED ACTION
```

And it must be traversable **backwards** at every step:

```text
ACTION → WHY? → SIGNALS → EVIDENCE → SOURCE
```

That is what makes the Command Center trustworthy.

# 3. GLOBAL RULES

These apply to **every** phase and are stated in full in `docs/README.md`. In brief:

| # | Rule |
| - | ---- |
| G1 | Keep FACTS / SIGNALS / SCORES / ACTIONS strictly separate. Do not mix them in one module or one UI block. |
| G2 | Scoring is deterministic code, never the model. AI interprets and writes; it never produces the number. |
| G3 | Missing data is `Data unavailable`, never `0`. Missing data lowers **confidence**, not health. |
| G4 | Nothing is displayed without an explanation. Never a bare `Priority: 92`. |
| G5 | The pipeline is traversable in both directions, down to the source record. |
| G6 | Read-only + recommendation. Nothing external happens without explicit human approval. |
| G7 | Never fabricate contacts, tickets, quotes, scores, signals, outcomes or company information. Fixtures are clearly labelled MOCK. |
| G8 | Nothing hardcoded that a human might want to argue about — weights, thresholds, cadences and policies live in config. |
| G9 | Respect the existing add-in's conventions: no build step, `window.C360` globals, `c360-` DOM prefix, no secrets client-side, pure engines, Node tests. |
| G10 | Do not break what exists. The scorecard is additive; Customer 360 keeps working at every commit. |

## PHASE 1 — Foundation, Identity & Data Model

→ `docs/phase-1-foundation-identity-data-model.md`

Inspect the existing Customer 360. Create the canonical account identity layer and the
normalised account/signal models. Do not break existing functionality.

**Scope**

- Audit of existing data and intelligence (the deliverable is `docs/phase-1-audit.md`).
- **Master Customer Identity** — one canonical id mapping to CRM account, email domain,
  ticket organisation, quote, billing account, MyGeotab database, camera portal, contract
  and renewal record. Names alone are not sufficient: `"ABC Logistics Inc."`,
  `"ABC Logistics"` and `"ABC Logistics LLC"` may be one company.
- **Identity confidence** per source-to-account mapping, with a configurable minimum
  threshold. A source below the threshold is NOT attached to the account.
- **Account segments** (Strategic/Enterprise, Mid-Market, Small Business, New Onboarding,
  Long-Term, Suspended, Seasonal) driving review cadence, renewal windows and priority
  expectations — configured in `accountSegmentRules`, never hardcoded.
- **Customer lifecycle** (Onboarding, Adoption, Mature, Expansion, Renewal, At Risk,
  Churned, Suspended). The same signal means different things by stage.
- `js/core/scorecardConfig.js` — the config skeleton every later phase extends.
- 20–30 labelled MOCK fixtures covering the MVP sample.

**No scores and no UI in this phase.**

**Known conflict to resolve here:** `js/intelligence/health.js` is deliberately
non-numeric by design (its header says so). The new brief needs a numeric 0–100 score
across five categories. Recommended resolution: leave `health.js` alone and add
`js/scorecard/healthScore.js` alongside it, with the qualitative wording becoming the
plain-language rendering of the numeric sub-scores. Record the decision in the audit.

**Exit:** identity resolves across sources with per-link confidence, low-confidence
sources are not attached, segments and lifecycle resolve with a stated basis, fixtures
exist, and the existing UI is unchanged.

## PHASE 2 — Health Engine & Data Confidence

→ `docs/phase-2-health-engine.md`

A transparent 0–100 Health Score from five independently scored categories.

| Category | Weight |
| -------- | -----: |
| Product & Device Health | 25% |
| Support & Service Health | 20% |
| Engagement & Relationship | 20% |
| Commercial & Retention | 25% |
| Outcomes & Value | 10% |

```text
Health Score =
  (Product Health      × 0.25)
+ (Support Health      × 0.20)
+ (Relationship Health × 0.20)
+ (Commercial Health   × 0.25)
+ (Outcomes Health     × 0.10)
```

Implemented deterministically in code. The model never determines this calculation.

**Category rules that matter**

- **Product & Device (25%)** — non-communicating devices, camera availability, portal
  usage, HOS activity, unused hardware, connectivity, utilisation. Do not invent metrics
  the data does not support.
- **Support & Service (20%)** — severity, age, recurrence, SLA breach, customer impact,
  escalation. **Do NOT use ticket count alone.** Twenty resolved low-severity tickets can
  be healthier than one critical unresolved one.
- **Engagement & Relationship (20%)** — last contact, response patterns, sentiment,
  stakeholder coverage, review cadence, decision-maker engagement. **Do NOT let email
  sentiment alone determine health** — it is capped until corroborated. Negative email +
  repeated complaints + competitor reference + escalation is a far stronger signal than
  one short frustrated email.
- **Commercial & Retention (25%)** — renewal date, past-due invoices, cancellation
  language, downgrade requests, competitor activity, quotes, orders. Joint-highest weight
  because commercial risk exists even when product health is good.
- **Outcomes & Value (10%)** — training, implemented recommendations, safety/fuel/
  utilisation improvements. Unavailable outcomes report `Outcomes data limited`; absence of
  evidence is not evidence of poor outcomes.

**Unavailable categories** report `Data unavailable`, re-normalise the remaining weights,
and say so. They are never scored `0`.

**Data Confidence** is a separate output — how complete and reliable the underlying data
is, from freshness, category coverage, source reliability, identity confidence, recent
activity and conflicting information:

```text
Health:     42 / 100
Priority:   91 / 100
Confidence: 84%
```

**Exit:** five independent sub-scores each with signals and a basis, the weighted formula
in code and hand-verified by test, nothing coerced to zero, confidence separate, and the
breakdown object able to reproduce the arithmetic with real values.

## PHASE 3 — Priority Engine & Critical Overrides

→ `docs/phase-3-priority-and-overrides.md`

The weighted health score MUST NOT be the only mechanism determining urgency.

**Order of operations**

```text
signals + health + segment + lifecycle
        ↓
  OVERRIDE ENGINE     -> a FLOOR on the priority level, with a reason and a source
        ↓
  PRIORITY SCORE      -> weighted 0-100, deterministic
        ↓
  { level, score, reasons, primaryReason }
```

An override sets a floor. It can raise urgency, never lower it.

**Override rules**

```text
P0   Explicit cancellation request        P1   Critical ticket beyond SLA
     Explicit competitor-switch request        Renewal within 90 days + negative signals
     Safety-critical issue                    Overdue commitment made to customer
     HOS/compliance-critical problem
     Executive escalation                P2   Quotation awaiting response beyond period
     Service outage                           Account review overdue
                                              Qualified expansion opportunity

P3   Healthy account / routine engagement / long-term nurture / non-urgent opportunity
```

Every fired override records WHY and FROM WHERE:

```text
P0 OVERRIDE

Reason:  Customer explicitly requested cancellation.
Source:  Email — Aug 20, 2026

This override takes precedence over the weighted health score.
```

**Priority score**

| Factor | Weight |
| ------ | -----: |
| Risk Severity | 35% |
| Time Sensitivity | 25% |
| Account Value / Strategic Importance | 20% |
| Overdue Commitments | 10% |
| Expansion Readiness | 10% |

```text
Priority =
  Risk Severity         × 0.35
+ Time Sensitivity      × 0.25
+ Strategic Importance  × 0.20
+ Overdue Commitments   × 0.10
+ Expansion Readiness   × 0.10
```

Implemented deterministically. The AI does not calculate the final number.

Priority is reported as **both** a level and a score (`P0` / `91 / 100`), where
`P0 = Immediate, P1 = High, P2 = Medium, P3 = Routine`, and:

```text
level = max( levelFromScore(score), overrideFloor )
```

**Every priority explains itself** — an ordered `reasons[]` with evidence, plus a
`primaryReason`. Never a mysterious score.

Note: cancellation / competitor / escalation detection in this phase is **deterministic
pattern matching** over source records, keeping the matched excerpt as evidence.
AI-assisted extraction arrives in Phase 8 and must not change any score.

**Exit:** tests prove health and priority are independent — a healthy account with one
critical unresolved issue comes out high-health and P0/P1.

## PHASE 4 — Action Queues

→ `docs/phase-4-action-queues.md`

Do NOT create one giant list. Four separate queues:

```text
SAVE     Cancellation, competitor threat, renewal risk, relationship deterioration
FIX      Technical escalation, billing issue, device problem, SLA breach, overdue support
GROW     Fleet expansion, new facility, new vehicles, unused product, new market
ENGAGE   Account review overdue, training required, inactive customer, stakeholder gap
```

Precedence when an account qualifies for more than one:

```text
SAVE  >  FIX  >  GROW  >  ENGAGE
```

One `primaryQueue` per account, plus full `queues[]` membership so the FIX evidence still
travels with a SAVE account — fixing the ticket is usually *how* you save the account.

Rules:

- Do not queue an account on health score alone. A low score is not a SAVE; a cancellation
  signal, renewal risk, competitor threat or measurable deterioration is.
- Do not put an account in GROW without a **qualified** opportunity. "No usage found for
  product X" is a product gap, not an opportunity.
- An account with nothing to do belongs in **no** queue. Do not manufacture an ENGAGE item
  to avoid an empty row.
- Queue counts therefore do **not** sum to the portfolio total. Label them accordingly.

Card contract for Phase 6:

```text
┌───────────────────────────────────────────┐
│ SAVE                                      │
│                                           │
│ ACME Transportation          P0           │
│ Cancellation signal                       │
│                                           │
│ → Prepare retention call                  │
└───────────────────────────────────────────┘
```

## PHASE 5 — Recommended Action Engine

→ `docs/phase-5-action-engine.md`

The system must go beyond `Contact customer.` Every recommendation contains:

```text
WHY   EVIDENCE   ACTION   OWNER   DUE DATE   DRAFT   CONFIDENCE
```

```text
RECOMMENDED ACTION

Why:       Customer has a critical camera issue open for 14 days and the
           ticket has exceeded SLA.
Evidence:  • Ticket #1234  • Opened Aug 6  • SLA breached Aug 9
           • Last customer update Aug 15
Action:    Escalate internally, obtain a confirmed resolution ETA, then
           proactively update the customer.
Owner:     Account Manager + Technical Support
Due:       Today
Confidence: High
```

An action is an **ordered list of steps**, not one sentence — note that the example
escalates internally *before* contacting the customer.

**Deterministic mappings**, held as config data rather than scattered branches:
cancellation, critical ticket, inactive quote, account review overdue, device health
problem, portal adoption decline, safety concern, competitor signal, overdue commitment,
and strong health + operational pain.

Where no mapping matches, emit **no** recommendation. A generic action is worse than none.

**Ownership** — Sean, Account Manager, Customer Success, Technical Support, Billing,
Sales, Product, Leadership, or combinations. When it cannot be determined: `Unassigned`.
**Do not guess.**

**Due dates** derive from urgency, with a nearer hard deadline (SLA, renewal, commitment,
quote expiry) overriding and being named:

```text
P0  Today            P2  Within 3–5 business days
P1  Within 1 day     P3  Routine
```

**Drafts** (customer email, internal escalation, meeting agenda, follow-up) MUST remain
drafts. The default implementation **must not** send — there is no send path in this phase
at all. A draft may only name a **verified** contact and may not assert a fact absent from
its evidence list.

Declined recommendations are recorded in `suppressed[]` with a reason. Silent omission is
indistinguishable from a bug.

```text
08:00 → Pull → Normalize → Detect signals → Calculate health → Calculate priority
      → Apply overrides → Generate actions → Update portfolio queue
```

  Do NOT require the model to run continuously. Controlled refresh, bounded concurrency,
  `Last updated` shown, manual Refresh control, and partial failure renders partial
  results with a per-source failure list.

Accessibility: priority is always conveyed as text, never colour alone.

```text
ACCOUNT HEALTH   42 / 100   AT RISK

Outcomes             72        Confidence          84%
```

Never `42 — At Risk` with no explanation.

**Score explanation drawer** shows the real arithmetic, using actual calculated values:

```text
HEALTH SCORE BREAKDOWN

Product & Device   61 × 25% = 15.25
Support            38 × 20% =  7.60
Relationship       47 × 20% =  9.40
Commercial         29 × 25% =  7.25
Outcomes           72 × 10% =  7.20
──────────────────

```

The rendered lines must sum to the rendered total. Do not hardcode the example numbers.

threshold it leads with the limitation rather than the number.

**Evidence panel**, grouped by source class, every entry reaching a real record or the

```text
WHY IS THIS ACCOUNT P0?

Internal:        • Ticket #1234 — Critical — Aug 6
                 • Ticket #1255 — Critical — Aug 12
Commercial:      • Renewal — Oct 15
Communication:   • Cancellation language — Aug 20
External:        • Competitor deployment mentioned — Aug 18   (identity match 90%)
```

Text-derived evidence shows the matched excerpt, so a false positive is immediately

**"What changed"** extends the existing `C360.signals.whatChanged()` with score deltas —
and never invents a previous value to compute a delta against.

fixtures. A narrative paragraph you cannot click into is exactly the failure this phase
exists to prevent.

## PHASE 8 — AI Layer & Human Approval

→ `docs/phase-8-ai-layer-and-approval.md`

**Only after deterministic scoring works.** The whole product functions without AI; AI
makes it more useful, not more correct.

**AI is for**

```text
Extracting signals                Identifying probable risks
Summarizing account history       Identifying probable opportunities
Interpreting unstructured notes   Explaining priorities
Interpreting emails               Generating action plans
                                  Drafting communications
                                  Preparing meeting agendas
```

**AI must NOT silently**

```text
Calculate health       Invent account activity
Calculate priority     Invent financial information
Invent evidence        Invent customer sentiment
Invent contacts        Take external actions
```

The dividing line as an implementation rule:

> AI may **propose a signal**. The deterministic engine decides whether it fires a rule,
> and the deterministic engine alone produces the number.

Enabling AI must change **no score anywhere** — that is a test, not an aspiration.

**Provenance is mandatory.** Every model-touched field carries `provenance`, the model id,
non-empty `sourceRecords` and the excerpt, and renders with a visible marker. A claim not
supported by a listed source record is a fabrication: drop the output, do not repair it.

**Human approval.** The system is READ-ONLY + RECOMMENDATION.

```text
AI RECOMMENDATION  →  USER REVIEW  →  APPROVE  →  ACTION
```

AI must never automatically send customer emails, cancel contracts, change pricing, issue
credits, modify devices, change CRM records, close tickets, change subscriptions, or commit
to customers. Exactly **one** gated code path can produce an outbound effect and it
requires an approval record naming the approver, the final edited content and the time.
`sendingEnabled` stays `false` after this phase; turning it on is a separate reviewed
decision. No bulk approval, no auto-approval, no timed approval. Human edits to a draft are
re-validated for evidence before approval.

Every AI insertion point has a deterministic fallback, and degradation is **visible**
(`AI summary unavailable — showing rule-based summary`), never silent.

The model API key never reaches the browser. The AI call is a gateway endpoint like every
other source.

## PHASE 9 — Feedback Loop & Success Metrics

→ `docs/phase-9-feedback-and-metrics.md`

The Phase 3 patterns and Phase 2 thresholds are guesses. This is the mechanism by which
they stop being guesses — not optional polish.

**Feedback** on every recommendation:

```text
Useful          Not needed
Incorrect       Already handled
```

Optionally: `Why was this incorrect?`

The four labels are **distinct** and must not be collapsed into thumbs up/down:

- **Useful** — right and wanted.
- **Incorrect** — the reasoning was wrong. *This is what indicts a rule.*
- **Not needed** — reasoning right, action unwarranted. Indicts the action mapping.
- **Already handled** — both right, work already done. Indicts data freshness.

Feedback attaches to the **rule that fired**, with enough context to reproduce the
decision (rule id, evidence ids, scores at the time, config version). It never mutates a
score or auto-suppresses a rule — suppression is a deliberate human config change after
reading the aggregate. Dismissing retains the record.

**Success metrics** — a simple analytics layer:

```text
Hours saved                     Critical response time
Recommendations accepted        Account reviews completed
Recommendations rejected        Quotes progressed
False-positive priority rate    Retention influenced
At-risk customers identified    Expansion influenced
```

**Do NOT attempt sophisticated predictive modelling initially. Start with measurement.**

Honesty requirements: `Hours saved` is an estimate from a configured constant and is
labelled as one. Accept/reject rates ship with the feedback response rate. False-positive
rate is reported **per rule**, never only globally. Retention and expansion influence are
**correlation only** and must say so. A metric whose inputs do not exist reports
`Not yet measurable`, never `0`.

```text
tests/fixtures/                   P1+ deterministic scenario fixtures
```

Engines are pure — same input, same output, no I/O. All I/O stays in the orchestrator and
services; all DOM stays in `js/ui/`. That split is what makes the rules testable in Node
without a browser.

adding a framework.

# 9. AI ROLE — SUMMARY

Use **deterministic code** for scoring. Use **AI** for interpretation and generation.

# 10. MOST IMPORTANT DESIGN PRINCIPLE

The system must NOT become a generic "AI customer summary."

The primary workflow is:

```text
DATA → SIGNALS → HEALTH → PRIORITY → ACTION
```

And the user must be able to go backwards at every step:

```text
ACTION → WHY? → SIGNALS → EVIDENCE → SOURCE
```

That is what makes the Command Center trustworthy.

---

# 11. FINAL IMPLEMENTATION RULE

Before changing anything:

1. Inspect the existing Customer 360 repository.
2. Understand its current architecture.
3. Identify what already exists.
4. Reuse existing APIs/services/components.
5. Do not duplicate existing account intelligence.
6. Add the scorecard as a new intelligence layer.
7. Keep scoring deterministic.
8. Keep AI explainable.
9. Keep external actions human-approved.
10. Build the portfolio view before attempting sophisticated autonomous behavior.

Do not claim an API integration exists if it does not.

Do not create fake customer data except clearly labeled development fixtures.

Do not fabricate contacts, tickets, quotes, scores, health signals, or company
information.

The finished product should be a **transparent Customer Portfolio Command Center** that
helps Sean decide:

> **Who should I care about today, why, and exactly what should I do?**
